# RepoProof 演示脚本

> 用途：初筛作品帖配图、3 分钟线上路演、90 秒录屏。  
> 原则：先示例、后真实仓库；先讲边界、再讲能力；不承诺“识别真假”，不给分数。

## 一、3 分钟路演脚本

### 0:00–0:20 问题与人设

**画面**：首页，鼠标停在仓库地址输入框。  
**动作**：不急着输入。

**台词**：

> 面试前十分钟，简历上写着：使用 FastAPI，包含自动化测试，采用 MIT 许可证。面试官问：在哪？大多数人会开始翻仓库。  
> RepoProof 做的事情，是把这句话变成一条能点开的证据。

### 0:20–0:55 示例：四种状态一次看全

**画面**：点击“使用示例数据”，进入结果页。  
**动作**：鼠标依次指过统计条上的四个数字，不要快速滚动。

**台词**：

> 先看一个固定快照。它不发起网络请求，也不消耗 GitHub 配额。  
> 四条声明，四种状态各一条：  
> 许可证声明 Apache-2.0，GitHub 识别 MIT，这是“元数据不一致”；  
> `tests/` 路径没有找到可访问证据，这是“公开证据不足”；  
> CI 这条遇到模拟的 429，这是“无法完成核验”；  
> FastAPI 这条在依赖清单里找到了声明，这是“发现公开证据”。

### 0:55–1:40 逐条看：证据在哪里，边界在哪里

**画面**：停在第一条“元数据不一致”。  
**动作**：点开证据链接，展示 LICENSE 文件；再回到结果页，对照卡片里的“支持什么/不支持什么”。  
**台词**：

> 先说不一致。声明是 Apache-2.0，仓库的 LICENSE 被 GitHub 识别为 MIT。两边都能点开复查，所以这条可以判“不一致”。  
> 但它只支持“许可证元数据与声明不同”，不支持“功能有没有实现”，也不支持“个人贡献”。

**画面**：滚到 `tests/` 与 CI 两条。  
**动作**：指一下“不支持什么”列表。

**台词**：

> 这两条更重要。`tests/` 没找到，产品写的是“公开证据不足”，不是“文件不存在”。  
> CI 遇到 429，产品写的是“无法完成核验”，不是“没有 CI”。  
> 平台限制、路径没找到，都不能算到项目头上。这是这个产品最克制的地方。

**画面**：滚到 FastAPI 那条。  
**动作**：点开 `backend/pyproject.toml` 的证据链接。

**台词**：

> 找到的那条，也只说“依赖清单里声明了 FastAPI”，不说“代码质量好”，也不说“这个功能是你做的”。

### 1:40–2:15 真实仓库：拿自己的项目跑一遍

**画面**：点右上角“重新查询”回到首页，输入 `https://github.com/bufan528/xunyun-jingchuan`，等待仓库信息加载。  
**动作**：添加 5 条核验对象；点“确认并核验”。

**台词**：

> 示例是固定的。再看一个真实仓库，我自己的项目。  
> 我加了五条：README、入口文件、测试路径、CI 路径、MIT 许可证。  
> 结果是 2 条找到公开证据，3 条证据不足。  
> README 和 `miniprogram/app.js` 能点开；`tests/`、`.github/workflows/` 和许可证没有找到可访问的公开证据。  
> 这不等于我没有做测试，也不等于项目没有许可证。它只说明：以当前公开材料，无法支持这三条声明。

### 2:15–2:40 Qoder 过程与工程结果

**画面**：切到终端 71/71 测试通过；再切到 Qoder Sites 公网页面。  
**动作**：展示提交 SHA、测试数量、公网地址。

**台词**：

> 实现上用 Qoder 完成规格拆解、规则、解析器、前端、测试和部署。  
> 判定口径由我逐条检查：404 不能写成不存在，license null 不能写成无许可证，429 不能写成证据不足。  
> 71 个用例全部通过，公网静态页无需登录。

### 2:40–3:00 收束

**画面**：点“复制分享链接”，展示只读证据页的只读横幅；再展示底部边界声明。  
**台词**：

> 结果可以一键复制成只读分享链接：面试官打开就能看，不能改内容，也不会重新请求 GitHub。  
> RepoProof 不做真假判断，也不判断你的个人贡献。  
> 它只做一件事：面试前十分钟，把简历里的项目描述，变成可点开、可复查的公开证据。  
> 公开证据不足，不代表项目没有实现。

## 三、现场故障预案

| 情况 | 处理 | 台词 |
|---|---|---|
| GitHub 403/429 | 立刻停止重试，切到案例库 | “产品把这种情况判为无法完成核验，不把平台限制算到项目头上。我们直接看一个固定快照案例。” |
| 网络断开 | 切到本地截图或录屏 | “证据链接在正常网络可以打开；这里用截图展示同一份结果。” |
| 真实仓库加载慢 | 等待 5 秒，仍慢就切示例 | “真实查询依赖 GitHub 公开 API，现场网络不稳定时以示例为准。” |
| 页面样式异常 | 刷新一次；仍异常用录屏 | 不现场调样式，不在评委面前 debug。 |
| 被问“为什么不是实时” | 说明快照与真实模式 | “示例是固定提交的快照；输入仓库地址才是实时查询。” |

## 四、常见问题与回答

**1. 这不就是人工看 GitHub 吗？**  
人工看仓库是逐文件浏览，结论不可复用。RepoProof 把声明拆成核验对象，固定到 commit，逐条给出状态、证据链接和“不支持什么”；同一份输入可以重复得到同一份结果。

**2. 为什么不用大模型做自由文本判断？**  
MVP 优先可复查。路径、依赖清单、SPDX 都能用确定性规则核对；自由文本判定容易把“没找到”说成“没有”，也会引入不可解释的分数。当前版本让用户确认核验对象，就是为了不替用户下结论。

**3. “公开证据不足”是不是说项目是假的？**  
不是。它只说当前公开材料无法支持这条声明。产品里明确写了：公开证据不足，不代表项目没有实现。

**4. 能判断个人贡献吗？**  
不能，也不做。提交作者、提交时间都不参与判定；产品不评价谁写了多少代码。

**5. 能覆盖多少简历描述？**  
目前覆盖三类可机械核验的声明：路径存在性、依赖清单声明、许可证 SPDX；另有目录清点，只用于发现。自由文本需要用户确认映射，不承诺全覆盖。

**6. 数据隐私怎么处理？**  
只读公开仓库；不登录、不上传简历、不保存输入；没有后端存储。

**7. 和简历评分、背调有什么区别？**  
不做分数、不做排名、不做通过率预测，也不做真假判断。只整理公开证据入口和证据强度边界。

**8. 为什么是四种状态，不是通过/不通过？**  
“没找到”“取数失败”“元数据冲突”“找到证据”是四种不同情况，混成两种会制造误判。四态是为了让失败原因可解释。

**9. 私有仓库或仓库删除怎么办？**  
当前只支持公开仓库。仓库不可访问时，对应声明无法完成核验，不做任何“存在/不存在”的推断。

**10. 下一步做什么？**  
补更多清单格式和导出能力，扩大真实仓库回归集；仍然不做贡献判断和真假判断。

**11. 分享链接是什么？**  
结果编码在 URL 片段里，打开是只读证据页：不重新请求 GitHub、不能修改内容，也不包含简历原文。

**12. 案例库是真的吗？**  
3 个公开仓库的固定提交快照，页面标明快照日期与 commit，证据链接可以回到 GitHub 原文复查。

## 五、演示前检查

- [ ] 公网链接在另一台设备/无缓存窗口可打开，零登录。
- [ ] 示例快照日期与 commit 显示正常。
- [ ] 真实仓库案例的 commit SHA 与截图一致。
- [ ] 首页三个案例都能打开，横幅写明“案例快照 / 不发起网络请求”。
- [ ] 生成一条分享链接，在另一台设备打开，确认只读页控件隐藏。
- [ ] GitHub 配额可用；不可用就直接走案例库，不反复重试。
- [ ] 375px 手机端首页和结果页各打开一次。
- [ ] 录屏文件本地备份；现场网络故障时可播放。
- [ ] 关闭通知、聊天窗口和其他标签页；不要露出个人信息。
- [ ] 计时演练两遍：3 分钟版不超过 3:10，90 秒版不超过 1:35。

## 六、不要说的话

- “AI 能识别简历真假。”
- “这个项目能判断真假/能证明是你做的。”
- “覆盖率 100% / 所有简历都能查。”
- “官方要求 90 秒视频。”（官方规则没有这条，90 秒只是内部演示口径。）
- “首创 / 第一 / 唯一。”
- 任何无法当场点开的百分比、排名或案例。
