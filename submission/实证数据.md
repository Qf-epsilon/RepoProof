### 方法

- 样本：8 个公开仓库（个人项目与常见开源项目混合），共 40 条简历式声明。

- 所有仓库固定到具体提交；示例与案例快照不发起网络请求，其余走 GitHub 公开 API。
- 采样日期：2026-11-27。样本不是随机抽样，声明为人工编写的简历式表述，用于检验判定口径，不代表真实投递简历。

### 两条典型

1. **expressjs/express 的 `tests/`**：声明“项目包含自动化测试”，结果是“公开证据不足”。但同一提交里存在 `test/`（114 个文件）。路径形状不匹配，不等于项目没有测试。

2. **bufan528/xunyun-jingchuan 的 `MIT`**：GitHub 未识别出可用的 SPDX 许可证元数据，结果写的是“公开证据不足”，而不是“无许可证”。

### 结论

- 33/40 条声明找到公开证据；没有一条“证据不足”被写成“文件不存在”或“无许可证”。
- 7 条“证据不足”里，4 条能在同一提交中找到形状不同的替身路径（如 `test/`、`backend/tests/`），1 条属于许可证识别差异，其余 2 条是路径本身没有可访问材料。
- 四态分开是必要的：把“没找到”和“没查成”混成“不通过”，会制造误判。
- 本次样本里 0 条“元数据不一致”：当声明按仓库实际情况填写时，冲突本身很少见。

### 限制

- 不判断功能是否实现、代码质量、测试覆盖率或个人贡献。
- 样本与声明为人工挑选，不是随机抽样；结果只代表这些仓库在固定提交下的公开材料。
- 许可证元数据由 GitHub 识别，可能随仓库与平台变化。
